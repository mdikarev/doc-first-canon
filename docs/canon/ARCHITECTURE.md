# Architecture

## Summary

Two layers: a deterministic **CLI** (`doc-canon`) owns schema, scaffold, structural validation, inventory, report merge for `source: cli` findings, index build, and bounded canon search; an **agent layer** (harness overlays for Cursor, Claude Code, and DSH: identical skill trees under `.cursor/skills/`, `.claude/skills/`, and `.dsh/skills/`; Cursor pointer rule / short `AGENTS.md` block; full-body `CLAUDE.md`; DSH reuses the `AGENTS.md`/`CLAUDE.md` always-on guidance and discovers skills under `.dsh/skills/`) owns interview, authorship, semantic audit, discrepancy dialogue, and the Scout → Expand retrieval protocol. Skills must call the CLI and must not invent structure outside the local contract. Agents search for a small working set before deep reads and fall back to INDEX-first Scout when search fails closed—quality over thrift. Search-first is mandatory when the index is available: `doc-canon search` / `code-index search` self-heal a stale index at the CLI layer (rebuild then serve) and record every successful search in `.doc-canon/probe-log.jsonl`; `doc-canon discipline` reports probe currency and gates on un-probed state.

## System context

| Actor | Role |
| --- | --- |
| Maintainer / user | Runs CLI; confirms contract changes; decides docs_stale vs code_stale |
| Cursor agent | Runs managed skills from `.cursor/skills/`; always-on via `.cursor/rules/doc-canon.mdc` and short `AGENTS.md` block; edits only `docs/canon/**` for canon work |
| Claude Code agent | Runs the same managed skills from `.claude/skills/`; always-on via full pointer-rule body in `CLAUDE.md` (does not load `.cursor/rules`); edits only `docs/canon/**` for canon work |
| DSH agent | Runs the same managed skills from `.dsh/skills/`; always-on via the `AGENTS.md` and `CLAUDE.md` blocks (no dedicated rule file); edits only `docs/canon/**` for canon work |
| Target repository | Holds `docs/canon/` (SoT), `.cursor/**`, `.claude/skills/**`, `.dsh/skills/**`, `AGENTS.md`, `CLAUDE.md`, optional `.doc-canon/` artifacts |
| npm package `doc-canon` | Ships CLI binary plus embedded templates, skills, and rules written to the selected harnesses (Cursor / Claude Code / DSH) on `init` / `upgrade-skills` |

## Building blocks

- **CLI entry & shared** (`src/cli.ts`, `src/paths.ts`, `src/version.ts`) — commander wiring, root/`.doc-canon` path helpers, package/`skills_stamp` constants
- **CLI commands** (`src/commands/*`) — `init`, `upgrade-skills`, `migrate`, `validate`, `check`, `report`, `index`, `search`
- **Contract** (`src/contract/*`) — parse and schema-check the YAML machine block in `CANON_CONTRACT.md`
- **Validate** (`src/validate/*`) — required files, headings, INDEX↔contract agreement, stamp checks
- **Agnostic ignore** (`src/agnostic/*`) — default exclude globs plus contract `policies.ignore` matching (via `micromatch`)
- **Inventory** (`src/inventory/*`) — language-agnostic tree walk; applies ignore helpers when listing the repo
- **Report** (`src/report/*`) — merge CLI findings; preserve `source: skill`
- **Scaffold / embedded** (`src/scaffold/*`, `embedded/**`) — default templates, skills, pointer rule, short `AGENTS.md` block, full-body `CLAUDE.md` upsert, harness-selected skill-tree copy (`.cursor` / `.claude` / `.dsh`)
- **Future plans skeleton** (`src/scaffold/ensure-future-plans.ts`) — idempotently ensures `future_plans/INDEX.md`, its templates, and the contract/INDEX rows exist; `init` creates a fresh required section, `upgrade-skills` migrates existing repos onto it without touching existing initiative prose
- **Required-gap ensure** (`src/scaffold/ensure-required-gaps.ts`) — creates missing required files/templates and INDEX rows vs the target contract only
- **Future plans validate zone** — `future_plans/*.md` other than `INDEX.md` are exempt from the "not listed in contract" orphan check; validate instead parses the Initiatives table in `future_plans/INDEX.md` (File column) and requires INDEX↔disk agreement plus required `FUTURE_PLAN` headings on each linked file. Initiatives are **not** per-file contract sections — only `future-plans-index` stays a registered, required section; root `INDEX.md` Sections never list individual initiative files.
- **Agent skills** (copied into the selected harnesses' skill trees: `.cursor/skills/`, `.claude/skills/`, `.dsh/skills/`) — bootstrap, write, audit, contract, future-plan
- **Index sync** (`src/index/*`) — hash-driven logical rebuild of a local BM25 index over `docs/canon/**/*.md`: unchanged content hashes are a no-op, any create/update/delete triggers a full rebuild from all current docs (no posting-level incremental updates); tokenization applies a light EN/RU stemmer inside `tokenize` (index and query tokenize identically) and a `tokenizer_version` in the manifest forces a full rebuild when it diverges (a content hash alone cannot detect a tokenizer change); `bm25-index.json` is `schema_version: 2` with an optional per-doc `heading_terms` field; poll-based watch (`doc-canon index --watch`, default 2000 ms, `--interval`) with a pid-locked single instance and `--stop`; a thin stable reader facade (`openCanonIndex` from `doc-canon/index-reader`) lets `searchCanon` consume the dual `.doc-canon/index-manifest.json` + `.doc-canon/bm25-index.json` artifacts without ad-hoc JSON parsing
- **Code AST index** (`src/code-index/*`) — the code-side probe, a separate artifact from the canon BM25 index: source-root discovery (VCS root up-search, manifest-driven roots for the five supported languages — TypeScript/JavaScript, Go, C#, Rust, Python — all shipped; extension fallback; explicit `.doc-canon/code-index.json` config > manifests > extension scan), a uniform tree-sitter WASM extraction pipeline (`@vscode/tree-sitter-wasm`, pinned) normalized into a shared `{ name, kind, signature, file, line, endLine, scope }` model, and syntactic references (same-file anchors, import edges, in-scope local bindings), where import edges resolve ESM `.js`/`.jsx`/`.mjs`/`.cjs` specifiers to their TS/TSX sources via a substitution pass in `resolveImportPath` (`.js`→`.ts`, `.jsx`→`.tsx`, `.mjs`→`.mts`, `.cjs`→`.cts`, plus `index.*` fallback; extensionless specifiers unchanged) and include call-site edges — identifier usages of imported names emit an `import`-kind edge to the definition file; member-access edges extend this — a local binding initialized from `new <Type>(...)` (imported, aliased, or same-file) emits `<Type>.<member>` edges for its `obj.method()`/`obj.field` usages, canonical name, syntactic only; in Go the same edge family covers composite/pointer-literal bindings (`x := &T{}` / `x := T{}` / `var x = T{}`) — same-file types resolve to the current file, qualified types (`reader.Handle{}`) resolve through the import edge map carrying the unqualified type name, and same-package types resolve via a post-processing pass (`resolveGoSamePackageReferences`); in C# the TS/JS `new Type(...)` pattern uses the `object_creation_expression` CST — same-file types resolve to the current file and imported types resolve via a post-processing pass (`resolveCSharpNamespaceReferences`) over a deterministic syntactic project model (file↔namespace from the file's `module` symbols — all namespaces declared in the file, nested included — plus per-file `using`-directive names), matching an unresolved `<Type>.<member>` against a unique class/interface/struct with own-namespace-first priority, then the `using`-union (exactly one distinct candidate file → edge): `using`-imported (`using App.Models;`), `using`-alias (`using R = App.Reader;` — edge carries canonical `Reader`), namespace-qualified (`new App.Widget()`), and explicit-typed target-typed `new()` (`Widget w = new();`); `using static`, `global using`, and `var w = new();` get no edge; in Rust the same edge family covers associated-function constructors — a binding initialized from `Type::new()` / `Type::default()` (`let`/`const` with a `call_expression` initializer whose `scoped_identifier` callee path is the type) resolves `x.method()` / `x.field` to a `<Type>.<member>`-named edge, same-file types to the current file and imported names through the import edge map (relative `use self::…` / `use super::…` item imports; crate-relative, bare crate-path, and external-crate imports, generics, and non-`new`/`default` associated functions emit no edge — no Rust cross-file pass); in Rust relative `use self::...` / `use super::...` declarations resolve module paths to `.rs` or `mod.rs` targets (bare crate-path `use foo::bar` emits no edge); in Python relative `from .module import name` statements resolve to `.py` or `__init__.py` targets (bare `import x` emits no edge), and the member-access edge family covers bare constructor calls — a binding initialized from `Type(...)` (an `assignment` whose right-hand side is a `call` with an identifier callee) resolves `x.method()` / `x.field` to a `<Type>.<member>`-named edge, same-file to the current file when the callee is a same-file `class` symbol and imported names through the import edge map when the callee is PascalCase (relative `from .module import Type` imports, `as`-aliases canonicalized — no Python cross-file pass); the cross-file post-processing passes are keyed by language in `src/code-index/resolvers/` (`CROSS_FILE_RESOLVERS`, keyed by grammar language — `go` → same-package, `c-sharp` → namespace/imported-type) so `sync.ts` stays language-agnostic, and per-language extraction differences (import conventions, member-access constructor patterns, resolution boundaries) are detailed in [CODE_INDEX.md](CODE_INDEX.md); default ignore excludes add `.worktrees` (the shared default ignore prunes worktree clones from code-source-root discovery and the language-agnostic repo inventory; the canon `docs/canon/**` corpus — built over `<root>/docs/canon` without ignore filtering — is unaffected); deterministic byte-identical dual artifact `.doc-canon/code-index-manifest.json` + `.doc-canon/code-ast-index.json` read via an `openCodeIndex` reader-facade (same dual-artifact pattern as `openCanonIndex`); hash-driven freshness (any create/update/delete or `grammar_versions` divergence triggers a full rebuild) with poll-based watch and a separate pid-lock; freshness is reported independently (`code_index_stale` → warn, `code_index_missing` → fail closed)
- **Retrieval** (`searchCanon` from `doc-canon/search`) — opens the dual index artifacts through `openCanonIndex`, ranks indexed documents, and reads live canon files for bounded snippet windows; scoring multiplies a term's contribution by 1.5 (`HEADING_WEIGHT`) when it is in the doc's heading set, scales final scores by 0.5 (`FUTURE_PLANS_WEIGHT`) for any doc whose path contains a `future_plans` segment at any depth (canon-relative or root-relative key), and expands the query from a live-read glossary only for query terms equal to a heading token unique across all term headings (adding that entry's full token set; additive, fail-open when `GLOSSARY.md` is absent — common/ambiguous tokens get no expansion); the thin `doc-canon search` CLI and skills consume the resulting context pack. The CLI `search` command self-heals a stale index (rebuild then re-run, `auto_reindexed` warning) when no watch owns it, and both search commands append one probe-log line per successful call; `check` merges `discipline` findings, and `doc-canon discipline` reports probe currency and exits ≠0 on un-probed state.
## Key flows

1. **Bootstrap** — `init` scaffolds, including a required `future_plans/INDEX.md` and harness-selected managed overlays (Cursor / Claude Code / DSH); `canon-bootstrap` interviews (empty) or extract-then-freeze (non-empty); then `validate`. After success, only `docs/canon/` is SoT.
2. **Feature change** — intentional new/changed behavior: coding agents invoke `canon-write` first (they do not edit `docs/canon/**` themselves), optionally sync/write a project-local design/plan when large, wait after substantial canon edits for user go-ahead, implement application code, then close with `canon-audit` (sibling-section and docs↔code drift that spot write may miss). Distinct from post-hoc everyday sync and from `code_stale` coding tasks.
3. **Validate** — structural fail-closed checks; need not write `report.json`.
4. **Check** — validate + inventory + CLI findings in `.doc-canon/report.json`; does not edit canon prose or `DISCREPANCIES.md`.
5. **Audit / resolve** — `canon-audit` semantic pass + user decision; apply order: successful apply → set `decision` → Open→Resolved when appropriate.
6. **Everyday sync** — human-invoked post-hoc `canon-write` / `canon-audit` after meaningful changes.
7. **Upgrade managed assets** — `upgrade-skills` refreshes the skill trees of the harnesses present in the repo (presence-detected via `.cursor/skills/`, `.claude/skills/`, `.dsh/skills/`; overridable with `--harnesses`), the Cursor rule, `AGENTS.md`, and `CLAUDE.md`, ensures the `future_plans/INDEX.md` skeleton (contract entry, INDEX row, templates, index file) exists for repos scaffolded before it was required, and bumps `skills_stamp`, without wiping canon content.
8. **Migrate** — precheck schema `1` → gap-fill → `upgrade-skills` (overlays + future_plans skeleton + stamp + validate).
9. **Future plans validate** — for `future_plans/*.md` (except `INDEX.md`): not orphans; must have a matching `future_plans/INDEX.md` Initiatives row; must carry required `FUTURE_PLAN` headings; root `INDEX.md` Sections stay contract-only.
10. **Retrieve canon context** — `openCanonIndex` → `searchCanon` (`doc-canon/search`) → CLI/skills. Ranking uses the P0b artifacts, while snippets come from live files; P4/P5 scoring (stemming in the tokenizer path, heading weights, `future_plans/**` downweight, live-glossary expansion) applies at search time. P1 owns retrieval and the pack, not index construction, artifact IO, hashes, or watch behavior. Since P7, a stale index is self-healed at the CLI layer when no watch owns it, and every successful search is recorded in the probe log.
11. **Build code AST index** — `doc-canon code-index build` discovers source roots, parses source files with tree-sitter WASM into the normalized model, and writes the deterministic dual artifact; unchanged hashes are a no-op, any change or `grammar_versions` divergence triggers a full rebuild. `code-index search` queries that artifact at search time; agent rules for code-index-first analysis land with P2c.

## Boundaries & non-responsibilities

- CLI does not invent prose; skills do not invent required files/section types/templates outside the contract.
- Canon skills never edit application code; code work goes to `DISCREPANCIES.md` with `coding_agent_prompt`.
- Content outside `docs/canon/` may be import sources during bootstrap, then is not SoT.
- Single root `docs/canon/` only (no multi-canon monorepo in MVP).

## Tech & constraints

- Node.js ≥20, TypeScript ESM package `doc-canon` 0.6.0
- Dependencies: `commander`, `yaml`, `micromatch`, `@vscode/tree-sitter-wasm` (code-index extraction)
- Unknown/incompatible major `schema_version` or too-old `skills_stamp` → validate fails closed
- Extra template headings allowed; missing required headings fail validate
- `policies.max_lines` default 400 (hinting / policy as implemented)
